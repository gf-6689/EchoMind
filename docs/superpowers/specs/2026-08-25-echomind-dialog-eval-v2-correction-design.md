# EchoMind Task 7：正式 Dialog Evaluation v2 校正设计

日期：2026-08-25  
状态：设计已确认，等待实施计划审核

## 1. 背景与证据

Task 7 已在 `data/eval/runs/dialog-eval-v1` 完成 35-case、43-turn 正式评测。产物结构完整，完整测试集曾达到 `88 passed`，但结果复核发现四类会影响正式统计口径的问题：

1. `dialog_eval_019` 的 Agent 返回空字符串，却被记录为成功并交给 Judge 评分，导致失败率和有效评分分母失真；
2. 冻结数据中有 6 个路由标签不符合当前 taxonomy 或路由代码定义；
3. 若干 `required_points` 超出了当前轮用户实际询问范围，可能奖励冗长回答并扭曲完整性评分；
4. `dialog_judge_v2` 能限制虚构“已经完成”的操作，但对无上下文依据的未来能力或操作承诺执行不一致。

此外，正式 v1 中出现 34,687 ms 的单轮 Agent 延迟，超过既定 30 秒质量门。现有证据不足以将该延迟归因于 BGE 初始化或 API 冷启动。

因此，`dialog-eval-v1` 只能作为历史基线和审计证据，不能直接作为最终可发布结果。本设计定义一个版本化、可复现的 v2 校正流程。

## 2. 目标

本次校正必须实现：

1. 将空字符串或纯空白 Agent 响应纳入现有失败与 fallback 语义；
2. 将 Judge 升级为 `dialog_judge_v3`，严格区分普通建议、无依据的未来操作承诺和虚构已完成操作；
3. 创建新的 `dialog_eval_v2.json`，修正已确认的路由标签并使每轮 `required_points` 与当前问题对齐；
4. 保留数据变更清单、数据集 SHA-256、Git revision 和独立运行产物；
5. 先完成离线测试、固定回答校准和独立预热，再重新执行完整 35-case；
6. 通过结构、失败语义、评分规则、路由、延迟和人工抽查门后，才允许发布 v2 指标。

## 3. 非目标

本次校正不做以下工作：

- 不覆盖、删除或改写 `dialog_eval.json`、`dialog-eval-v1` 或任何历史 Smoke/校准运行；
- 不通过修改生产 Agent Prompt 来追求更高评测分数；
- 不根据本次模型预测反向修改仍可辩护的边界标签；
- 不用关键词后处理强制修改 Judge 分数；
- 不更换 Agent、Judge 模型或服务商；
- 不将受控上下文评测描述为真实 retrieval/RAG 评测；
- 不在 v2 验收前更新简历指标或宣布 Task 7 完成；
- 不在本轮扩大为详细分阶段延迟埋点改造。

## 4. 方案选择

采用方案 A：版本化校正并重新评测。

该方案保留 v1 全部历史证据，通过代码修复、Judge v3、数据集 v2、固定校准、独立预热和全新正式运行形成可审计链路。

未采用的方案：

- **直接后处理 v1 指标**：无法修复空响应语义、冻结数据标签和 Judge 规则，统计结果不可复现；
- **只修复空响应后重跑 v1 数据**：仍保留错误路由标签、问题外必答点和 Judge 偏宽问题；
- **增加完整延迟分段埋点后再运行**：会显著扩大当前修复范围；若独立预热后仍超门，再单独设计诊断方案。

## 6. 空响应失败语义

`BaseAgent` 从 LLM 提取文本后，必须在返回成功前检查内容。`""`、仅空格、制表符或换行的内容都视为调用失败。

失败进入现有 orchestration 语义：

1. 首选 Agent 空响应时，允许现有 fallback 继续尝试；
2. fallback 成功并返回非空文本时，最终案例可继续评测；
3. 所有候选 Agent 均失败时，最终结果必须记录 `agent_failed = true` 和明确、无密钥的错误原因；
4. Agent 失败的 turn/case 必须设置 `judge_skipped = true`，不得调用 Judge，也不得计入有效 Judge 分母；
5. 正常非空响应、路由和现有异常处理行为保持兼容。

该规则应在生产 Agent 边界修复，而不是只在评测脚本中检查，从而避免其他调用方把空响应当作成功。

## 7. Dialog 数据集 v2

### 7.1 路由标签校正

仅修正下列明确违反 taxonomy 或当前路由定义的标签：

| Case | v1 | v2 | 理由 |
|---|---|---|---|
| `dialog_eval_016` | `technical_login / technical` | `account_security / billing` | 陌生设备登录属于账户安全 |
| `dialog_eval_021` | `order_status / general` | `logistics / general` | 用户询问承运商物流轨迹 |
| `dialog_eval_026` | `refund / billing` | `payment_issue / billing` | 首轮只陈述重复扣款，尚未提出退款诉求 |
| `dialog_eval_027` | `logistics / general` | `request / general` | 用户核心诉求是修改地址 |

| `dialog_eval_034` | `escalation / general` | `escalation / escalation` | 升级处理由 escalation Agent 承接 |

其余边界案例保持冻结，不根据模型输出修改标准答案。

### 7.2 `required_points` 对齐原则

每一轮必答点必须：

- 直接回答当前轮用户实际提出的问题；
- 只包含完成当前操作所必需的条件或下一步；
- 不把未被询问的价格、渠道、限制或功能介绍设为必需项；
- 在多轮对话中使用必要历史，但不要求机械重复前文；
- 允许控制上下文保留额外事实，额外事实不自动成为必答点。

已确认至少调整：

- Case 001：只要求回答人工客服工作时间；
- Case 003：只要求回答积分有效期；
- Case 006：只要求回答滤芯更换周期；
- Case 008：只要求回答会员权益；
- Case 009：只要求回答购买渠道；
- Case 030 第 3 轮：只要求回答发货时间，不重复缺货退款信息。

实施阶段必须逐轮复核全部 43 个 turn。任何额外校正都要进入变更清单；不得改变用户问题和核心受控事实，除非另行发现明确数据错误并先停止请求审核。

## 8. Judge v3 评分规则

Judge 继续使用独立 client、固定 system rubric、受边界保护的不可信 JSON 输入和结构化 tool 输出。结果字段、四个基础维度、算术 `overall`、重试和失败语义保持兼容。

`PROMPT_VERSION` 更新为 `dialog_judge_v3`，并增加以下强制区分：

### 8.1 普通建议或礼貌表达

例如“建议稍后重试”“请注意查收”。只要没有声称系统能执行具体操作，就不因该表达扣分。

### 8.2 无依据的未来能力或操作承诺

例如“我可以帮您转接”“我会为您提交审核”“我帮您登记并反馈”。若控制上下文没有授权这种能力：

- `accuracy <= 0.75`；
- `helpfulness <= 0.75`；
- `reasoning` 必须指出具体承诺和触发的上限。

### 8.3 虚构已经完成的操作

例如“已经为您提交退款”“工单已创建”“已完成转接”。若控制上下文没有证明该操作已完成：

- `accuracy <= 0.50`；
- `helpfulness <= 0.50`；
- 该 turn 不得判为通过；
- `reasoning` 必须指出具体虚构操作。

已有 v2 的其他规则继续保留，包括无依据的流程/原因/时限/材料要求、潜在敏感材料、上下文矛盾、严重冗长或破损格式以及多规则取最严格上限。

## 9. 测试与固定校准

### 9.1 TDD 测试矩阵

必须先观察新增测试失败，再做最小实现。至少覆盖：

1. 空字符串、空格和换行均不能产生成功 Agent 结果；
2. 首选 Agent 空响应、fallback 成功时最终结果有效；
3. 所有候选 Agent 失败时记录 `agent_failed`、错误原因和 `judge_skipped`；
4. Agent 失败案例不进入有效 Judge 分母；
5. 正常非空响应不回归；
6. 元数据记录 `dialog_judge_v3`；
7. Judge v3 rubric 同时冻结未来承诺、已完成操作和普通建议规则；
8. 现有解析、聚合、持久化、安全和完整测试集全部通过。

### 9.2 固定回答真实 Judge 校准

固定校准案例至少包含：

- 优质、完整且无越权的回答；
- 缺少必答点的回答；
- 无依据承诺未来转接、登记或提交；
- 虚构已经完成退款、转接或建单；
- 仅提供普通建议的回答；
- 通过离线测试模拟 Agent 失败或空响应，证明 Judge 被跳过。

校准通过要求：

- 所有缺陷案例满足冻结的评分上限；
- 普通建议不误触发越权扣分；
- 输出稳定解析，真实校准运行无意外 Agent/Judge 调用失败；
- 每条 reasoning 明确说明触发或未触发的规则；
- 保存校准输入、输出、指标、元数据和执行证据。

若校准失败，保留目录并停止；不得放宽已确认上限或增加关键词分数覆盖。

## 10. 独立预热与延迟门

正式评测前，使用与正式运行相同的 Agent、Judge、BGE 模型和配置执行一个独立受控案例：

- 结果写入 `dialog-warmup-v3`；
- 预热结果只用于加载本地模型、建立远端连接和记录冷启动，不计入 35-case 指标；
- 不复制、恢复或合并到正式运行；
- 预热失败时停止，不执行正式评测。

正式 v2 仍使用 `agent_latency_p95_ms <= 30000` 作为质量门。若预热后仍超门，保留完整运行证据并停止发布，另行诊断模型 API、重试、路由/Agent 调用和本地初始化，不对原因作无证据推断。

## 11. 正式 35-case 执行

正式运行必须：

- 使用 `dialog_eval_v2.json`；
- 使用 `dialog_judge_v3`；
- 写入全新的 `dialog-eval-v2`；
- 不使用 `--resume`，不继承 v1 的任何预测；
- 重新生成全部 35 个 case、43 个 turn。

## 12. 强制停止条件

出现任一情况即停止验收，不发布 v2 指标：

- Python 进程退出码非 0；
- 三个正式产物缺失或 JSON/JSONL 无法解析；
- 不是恰好 35 个 case、43 个 turn，或 ID、顺序、计数不一致；
- 存在空白 `agent_response` 却未标记失败；
- Judge 评审了 `agent_failed = true` 的案例；
- 数据集 SHA-256、Git revision、Judge 版本或上下文模式不正确；
- Judge 固定校准未通过；
- 正式运行预热后 `agent_latency_p95_ms > 30000`；
- 出现无法解释的异常分数或评分规则执行不一致。

真实 Agent/Judge 调用失败可以被系统如实记录，但包含该失败的运行不能作为最终可发布结果。必须保留证据、调查原因并使用新的运行目录重跑。

验收必须同时核验：

8. 所有低分、失败和路由不匹配案例的人工复核；
9. 四维均值、算术 `overall`、pass rate 和延迟统计；
10. 完整测试集通过；
11. 数据变更清单、固定校准、预热和正式运行证据齐全；
12. v1 数据和运行产物保持不变。
